# Agent queue

How the agent queue schedules, launches and reports on Linear tickets, and what it writes where.

Tickets carrying a Linear `agent:*` label (Agent group, Codeware team) are worked by the
`/work-queue` skill (`.claude/skills/work-queue`). It plans into the ticket, hands planned
steps to the `implementer` subagent (`.claude/agents/implementer.md`, Sonnet) in a worktree
per ticket, asks in Linear instead of waiting in the terminal, and keeps going until a limit
of what waits on Håkan. The skill holds the queue order, the labels and how a gate asks.
When a split's sub-issue has all its blockers done, the queue lists it as ready to label
(`COD-n label`) among what waits on Håkan; only he sets `agent:ready`.

To start an attended session, run `cdwr agent attend [COD-n]` from anywhere: it moves `codeware-queue` to `origin/main` (installing when the lockfile changed) and starts `/work-queue` there in the same terminal (`--no-start` prints the line instead). A session started on a detached checkout that is behind main warns at start and names that one command (the SessionStart hook, `tools/cdwr/agent-queue/session-start.sh`).

The scheduler runs in the NUC's agent container, plan-only every 10 minutes; `cdwr agent status --host <host>` says what it would take next. The Mac is attended-only: `cdwr agent install` there sets up the attended side (the script copies, the Linear app's Keychain items, `agent_linear`), `--scheduler` adds a launchd job (a plain `install` keeps an existing one current), and `cdwr agent uninstall` removes it (`--worktree-remove` takes the planner checkout too) and keeps the session side. Without the job, bare `status` shows the attended rows and `pause`, `resume` and `run` name the host that has the scheduler; `status`, `notify`, `pause`, `resume` and `run` take `--host <host>` to act on the container's queue over ssh (`run` there wakes its loop). Any other `cdwr` command in the container, such as a hand-off, is `cdwr agent exec --host <host> -- <args>`, which runs it through `secrets.sh` with the vault's keys; a plain `docker exec` has none. Launchd runs an installed copy of
`tools/cdwr/agent-queue/run.sh` (and its `watch.jq`, `waits.sh`, `implement.sh` and `github-app.sh`), so a merged change to its guardrails
waits for the next `install`. Before planning, the same job watches the PRs of `agent:working`,
`agent:needs-input` and `agent:review` tickets and sends a notice when a review PR leaves the merge
queue, fails or conflicts with main, or any of them merges with hand-offs left. A ticket merged outside review is
relabelled `agent:review` with a **Next:** line naming its hand-offs. After the watch, a parent whose
agent split finished (every sub-issue Done or Canceled, at least one Done and one agent work) is set
Done with an `**Agent: closed**` comment. Those are the job's two Linear writes. Then it reads
Renovate's open PRs into `renovate.json`: an untended one whose checks fail, or that conflicts with
main on a branch carrying a commit not by Renovate, is queue work (`PR 754`, held by the limit), until
a `renovate` ticket carries it as an attachment. A session files that ticket; a mechanical fix goes on
the agent's own branch, never Renovate's, which automerges an edited non-major PR once green.
In the NUC's container the loop wakes on Linear and GitHub events and new desk commands (`cdwr agent listen` on Supabase Realtime, publishable key `AGENT_SUPABASE_ANON_KEY`), with a run every hour as the fallback; without the listener it polls every 10 minutes. An attended session's `wait.sh` starts the same listener from its checkout, with a state file of its own, and re-picks every 10 minutes as its fallback, or every minute without the listener (no `AGENT_SUPABASE_URL` and `AGENT_SUPABASE_ANON_KEY` in `tools/cdwr/.env`).
Each run also sends its telemetry to the `agent-queue` Supabase project, which the Agent Desk reads: tables `runs`, `usage` (`cdwr agent usage`), `usage_hours` (the same spend per whole UTC hour over every Claude project on the host, sent every run and kept 14 days), `activity` (`cdwr agent activity`, from Linear's issue history), `sessions` (each session's heartbeat with its state and detail; an `ended` one leaves the desk at once), `queue_state`, `host_metrics` (the container's load, memory and disk, kept 7 days; the desk's NUC tile), `plan_usage` (the plan's 5-hour and weekly usage from the Mac's status line, `cdwr agent statusline install`; the desk's Plan usage tile, with `usage_hours` as its hourly breakdown), and `issue_events` written by the `linear-webhook` Edge Function, `github_events` and `builds` by `github-webhook`, `reviews` by the daily review run and `review_dismissals` by the desk's `dismiss` (env `AGENT_SUPABASE_URL` and `AGENT_SUPABASE_SERVICE_KEY`). It writes no Linear document. The desk writes only through the `desk-command` Edge Function, which checks a per-device token against `DESK_CONTROL_TOKENS` and stores each action in `desk_commands`. The same desk runs on the phone as a web app the NUC serves to the tailnet (`apps/desk/Dockerfile`, the `desk` service in `apps/agent-host/compose.yaml`, `tailscale serve`; the runbook is in `tools/cdwr/README.md`, "The desk on the phone"). The scheduler applies a host's pending ones at the start of each tick, before its pause check; `limit` and `cap` land in the queue home's `limit` and `implement-cap` files, which override the PR limit of 5 and `AGENT_QUEUE_IMPLEMENT_CAP_USD`. A review row's **Copilot review** and **Merge** buttons send `copilot` and `merge`, the scheduler's GitHub writes besides its own Copilot request below: as the `codeware-agent` app, on a PR its watch holds for that ticket, after reading it again (`desk_verdict` in `watch.jq`). A merge joins main's merge queue and ends like one on GitHub; a Copilot request the app can't make falls back on `AGENT_COPILOT_TOKEN` (`tools/cdwr/README.md`).

The scheduler also requests Copilot itself. The ruleset's automatic Copilot review runs only for a PR author with a Copilot seat, so it skips every PR the app opens. When the watch reads a ticket parked on `Waiting: copilot` for an open PR that has no Copilot request or review, it asks once for that PR (`copilot_request` in `run.sh`, the same request as the desk's button, so in practice as `AGENT_COPILOT_TOKEN`) and stores the outcome as `copilotAsked` on the PR's watch entry. The 20-minute Copilot wait then counts from that request. A failed request is not retried: it sends an `action` notice, and the desk shows the wait in Waiting on you with the Copilot button, as it does for a wait no request reached within 5 minutes (the scheduler down, or the PR not yet attached in Linear).
The `queue_state` row carries an `Attended:` line saying whether an attended `/work-queue` has something to do, and `cdwr agent status` shows it too. It also carries `watch`, the host's watch.json (the PRs of agent-labelled tickets with their state, checks, Copilot review and unresolved threads), and `renovate`, its renovate.json; a Mac without the scheduler reads both for its attended rows and its wait.
Once a day, in the first idle run after 06:00, the job runs `/suggest-improvement`, which proposes one evidence-led improvement as a `Source: agent-idea` ticket or records "nothing today"; the `queue_state` row's `Suggested:` line and `cdwr agent status` show it. Accept it with `agent:ready`, discard it by cancelling with one word in a comment.
Once a day, on an idle run the suggestion leaves (after `AGENT_QUEUE_SUGGEST_HOUR` too), it runs `/review-backlog`. The run writes the queue view (the tree and the audit candidates) to `review-view.json` and the last 90 days of `review_dismissals` to `review-dismissed.json` in the queue home, each with the ticket, kind, key and fix of the stored finding it names (dismissals hold for 90 days, and the desk reads the same window), and the session writes its brief, actions and findings to `review-out.json`. It may write only that file and `feedback_review_taste.md` in the memory directory, and it ends with `REVIEWED <n> actions` or `failed: <line>`. Then `cdwr agent review-check` validates the file and prints the row, which goes into the `reviews` table; a file it refuses, or one holding secret-like text (the table is public), stores nothing and records a warn, as does a row that could not be stored (`failed: not stored`). The session's `--disallowedTools` keep it from reading `.env*`, the cdwr files and the Linear credentials. The file's findings carry no id: the check derives each one from its kind, ticket and key, so a dismissal holds across runs. `review-ran-on` and `review-ran-at` (epoch seconds) stamp the start, and a run that stores no review removes `review-ran-at` again, so only a stored review holds the hour. The budget is `AGENT_QUEUE_REVIEW_BUDGET_USD` ($5) and `AGENT_QUEUE_REVIEW_DAYS` (1) sets the interval, 0 switching the schedule off. The desk's `review` command writes `review-requested`, which makes the next idle run a review whatever the hour or the interval (also with the interval at 0) and is removed when that run starts, before the suggestion is considered; it is refused for an hour after a review (`a review ran at HH:MM UTC`), at once by the `desk-command` Edge Function from the newest `reviews` row, with the scheduler's own check as a backstop. The desk's `dismiss` command is handled by the `desk_dismiss` rpc into `review_dismissals` and never reaches the scheduler. The `queue_state` row's `review` column holds the last outcome after its UTC minute; the desk shows it beside Review now when it is newer than the press (requested, accepted, refused or failed), `--check` prints the gate (`review: due`, `ran today`, `requested`, `not before`, `off`) and the devlog takes an idle run only when the review does not.
Once a week, on an idle run the suggestion and the review leave, it runs `/devlog-draft`, which drafts at most two devlog posts in the cms from the pull requests merged since the last one, or records "nothing this week"; each draft sends an `action` notice to publish or delete it in the admin; the `queue_state` row's `devlog` column holds the last outcome, `cdwr agent status` shows the gate (due, done, not before, off), and `AGENT_QUEUE_DEVLOG_DAYS=0` turns it off.

When that work waits and no session is alive, the job starts one itself: `implement.sh` runs
`claude -p "/work-queue implement-only once key=\"<key>\""` detached, with deny-by-default permissions, a
per-run budget (`AGENT_QUEUE_IMPLEMENT_BUDGET_USD`, $15) and a daily cap
(`AGENT_QUEUE_IMPLEMENT_CAP_USD`, $40) kept in `implement-spend.jsonl`. It resumes approved,
answered or reviewed work only, and never starts a new ticket. It reaches Linear on both hosts
through Linear's own MCP server, signed with a token of the queue's own Linear app, so its writes
are the app user's and not Håkan's (`AGENT_QUEUE_LINEAR_MCP`, the credentials and the token cache
are in `tools/cdwr/README.md`); a run without Linear tools doesn't start. The queue tells its own
comments from Håkan's by that author (`is_agent` in `watch.jq`), and never starts a ticket whose
`agent:ready` the app added (`refused` in the queue view). On GitHub it acts as the
`codeware-agent` app (`github-app.sh`, credentials in `tools/cdwr/.env`), never as Håkan, so
main's rulesets apply to it; without the app it does not start. The session takes the key's work
first (`wait.sh --runnable` lists what it may take); when it can't, it ends with
`not tried: <key> · <reason>` and the launch is recorded `untried` and not counted. After two
launches that change nothing it stops and sends the "Start /work-queue" notice instead. `cdwr agent pause` stops
launching too.

An attended Mac session stays visible to the NUC because its session hook copies each session file into the NUC's container (`cdwr agent mirror set --host agent-host`, once). So the NUC launches nothing a live Mac session holds: while that session is polling, any other ticket may launch there; while it is working, only a comment on a merged ticket does. The claim line decides who has a ticket, and a session that loses the race leaves it alone. The hook runs from the checkout the session started in, which must be on a main that includes the mirror support: `cdwr agent attend` does that.

Every run also audits the tickets (`audit` in `watch.jq`), report-only: it changes nothing in Linear. A gap is a state the queue cannot resolve by itself, and each carries what is wrong and the one fix. The kinds are `held`, `review-no-pr`, `merged-not-done`, `closed-pr`, `label-on-closed`, `two-labels`, `needs-input-no-question`, `unlabelled` and `launch-guard`. Four more are candidates for a later AI review, worded "check" and marked `candidate: true`: they stay in the view's audit and the tree's `gaps`, but send no notice and are not in the `Gaps (n)` count: `done-with-open-rows` (a ticket Done within 14 days whose Status table still has rows other than Done, Dropped or Skipped), `parent-status-stale` (a Status row naming a sub-issue says the opposite of its state), `untouched` (open, no agent label, not updated for 10 days, its parent updated since) and `decision-unasked` (a Status row says decision or Håkan picks, with no `agent:needs-input` and no agent question). The Status column is the one headed State or Status, else the last. A gap's `what` stays short and its `rows` array carries the row texts. They read every open COD ticket plus those Done within 14 days (`TREE_QUERY` in `lib.sh`, read by the run only, 200 at most, kept in `tree-nodes.json` for `AGENT_QUEUE_TREE_TTL_MIN` minutes, 15 by default, and reused when a read fails), where the other kinds read the agent tickets. The audit and a `tree` of every open COD ticket, as roots with their sub-issues, are keys of the queue view, so `queue-view.json`, `queue_state.view`, `cdwr agent status` (a `Gaps (n)` note) and the desk (a Gaps group on the queue sheet, and the Ticket tree page, opened from the header's Tree button, with each ticket's state, agent label, pick position (`position`: its 1-based place in the order `next` and the held tickets give, null when the queue never picks it; roots and children sort by the lowest position in their subtree, then by `queue_order`), PR, open blockers and gaps, its plan progress, live session, PR checks and age, and Open/All and Gaps-only filters) show them. The desk's header search finds a ticket by id or title among everything the desk has loaded, and opens a Ticket sheet (`#ticket/COD-n`) with all the desk holds for it. A stale claim or an unclaimed working ticket is no gap: the pick already takes it over. `audit-seen.json` maps each gap id to `{ first, told }`: a gap that has stood for 15 minutes and was not yet told sends one action notice, `Gap: <what>. <fix>`, so a state that settles by itself stays quiet; more than 3 due in a run send one summary instead; a gap that closes and returns starts over. `--check` sends nothing. The audit output goes through files, never arguments, since it outgrows the argument limit.
