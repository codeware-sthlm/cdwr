# Agent queue

How the agent queue schedules, launches and reports on Linear tickets, and what it writes where.

Tickets carrying a Linear `agent:*` label (Agent group, Codeware team) are worked by the
`/work-queue` skill (`.claude/skills/work-queue`). It plans into the ticket, hands planned
steps to the `implementer` subagent (`.claude/agents/implementer.md`, Sonnet) in a worktree
per ticket, asks in Linear instead of waiting in the terminal, and keeps going until a limit
of what waits on Håkan. The skill holds the queue order, the labels and how a gate asks.
When a split's sub-issue has all its blockers Done or Canceled and its report asks nothing first,
the scheduler labels it `agent:ready` itself (see below). One that asks first is listed as ready
to label (`COD-n label`) among what waits on Håkan. Otherwise only he sets `agent:ready`.

Plans approve themselves on every path. A session records its approval under Decisions and posts
`**Agent: plan approved**` with the decisions worth checking; reply to stop it. A plan-only run
keeps `agent:ready`: such a ticket is `plan_approved` in `watch.jq` and becomes a `plan approved`
pick, held by the limit like a ready ticket, and the scheduler launches an implement-only run for it.
A ticket whose report (the text before `## Plan`) holds `**Ask me before implementing**`, or a
heading or bold line starting "Open question", keeps the old `**Agent: plan ready**` gate. A
question only Håkan can answer stays a needs-input gate.

No plan-only run starts while an attended `/work-queue` session is alive or waiting at a prompt, a
mirrored one from the Mac included: that session plans what it claims, and a run beside it raced
its claim. The scheduler notes `skip: a /work-queue session is alive, it plans its own`,
and `--check` prints the same line. A launched implement session (`kind` in its session file) never
claims new work, so it holds nothing back, and neither does an attended one while the queue is at
the limit, since it starts no new ticket then. A tick whose attended read failed plans nothing and
notes why. A plan-only run that finds the ticket claimed when it
reads it again before writing ends with `not planned: COD-n · <why>`, which the scheduler notes as
a skip instead of `fail: planned nothing`.

To start an attended session, run `cdwr agent attend [COD-n]` from anywhere: it moves `codeware-queue` to `origin/main` (installing when the lockfile changed) and starts `/work-queue` there in the same terminal (`--no-start` prints the line instead). On the Mac it also runs `cdwr agent install --yes` from that checkout when the installed queue scripts differ from main's, before the session starts; if that fails it stops and names the command to run by hand. In the container it leaves the scripts alone. A session started on a detached checkout that is behind main warns at start and names that one command (the SessionStart hook, `tools/cdwr/agent-queue/session-start.sh`).

The scheduler runs in the NUC's agent container, plan-only every 10 minutes; `cdwr agent status --host <host>` says what it would take next. The Mac is attended-only: `cdwr agent install` there sets up the attended side (the script copies, the Linear app's Keychain items, `agent_linear`), `--scheduler` adds a launchd job (a plain `install` keeps an existing one current), and `cdwr agent uninstall` removes it (`--worktree-remove` takes the planner checkout too) and keeps the session side. Without the job, bare `status` shows the attended rows and `pause`, `resume` and `run` name the host that has the scheduler; `status`, `notify`, `pause`, `resume` and `run` take `--host <host>` to act on the container's queue over ssh (`run` there wakes its loop). Any other `cdwr` command in the container, such as a hand-off, is `cdwr agent exec --host <host> -- <args>` (a hand-off for the NUC is written as the one line `pnpm cdwr agent exec --host agent-host -- <command> --yes`, never a shell inside the container; a command that runs `gh` gets the app's token), which runs it through `secrets.sh` with the vault's keys; a plain `docker exec` has none. Launchd runs an installed copy of
`tools/cdwr/agent-queue/run.sh` (and its `watch.jq`, `waits.sh`, `implement.sh`, `linear-tools.txt` and `github-app.sh`), so a merged change to its guardrails
waits for the next `install`, which `cdwr agent attend` runs when the scripts drift. Before planning, the same job watches the PRs of `agent:working`,
`agent:needs-input` and `agent:review` tickets and sends a notice when a review PR leaves the merge
queue, fails or conflicts with main, or any of them merges with hand-offs left. A ticket merged outside review is
relabelled `agent:review` with a **Next:** line naming its hand-offs. After the watch, a parent whose
agent split finished (every sub-issue Done or Canceled, at least one Done and one agent work) is set
Done with an `**Agent: closed**` comment. Right after, a split's next part (`label_parts` in
`run.sh`) whose blockers are all Done or Canceled and whose report asks nothing first is labelled
`agent:ready`, with an `**Agent: labelled ready** every blocker is closed: …` comment, a `labelled`
record and an info notice. A part that already carries that comment, or is listed in
`labelled-parts` in the queue home, is never labelled again, so a part Håkan unlabels stays
unlabelled whichever host labelled it. `ready_by_app` lets the queue's own label through only on a
sub-issue carrying that comment whose report asks nothing first. Those are the job's three Linear writes. Then it reads
Renovate's open PRs into `renovate.json`: an untended one whose checks fail, or that conflicts with
main on a branch carrying a commit not by Renovate, is queue work (`PR 754`, held by the limit), until
a `renovate` ticket carries it as an attachment. A session files that ticket; a mechanical fix goes on
the agent's own branch, never Renovate's, which automerges an edited non-major PR once green.
In the NUC's container the loop wakes on Linear and GitHub events and new desk commands (`cdwr agent listen` on Supabase Realtime, publishable key `AGENT_SUPABASE_ANON_KEY`), with a run every hour as the fallback; without the listener it polls every 10 minutes. An attended session's `wait.sh` starts the same listener from its checkout, with a state file of its own, and re-picks every 10 minutes as its fallback, or every minute without the listener (no `AGENT_SUPABASE_URL` and `AGENT_SUPABASE_ANON_KEY` in `tools/cdwr/.env`).
The CDWR Desk (dark only) has two views, switched in its header: Agent, the work queue (what it does next and what waits on Håkan), with the pages Agent health (the NUC, versions and health checks) and Tree; and Platform, production (the tenants, their health and the problems below). Each switch button shows its view's count, what waits on Håkan and the open problems, and the choice is remembered per device.
Each run also sends its telemetry to the `agent-queue` Supabase project, which the CDWR Desk reads: tables `runs`, `usage` (`cdwr agent usage`), `usage_hours` (the same spend per whole UTC hour over every Claude project on the host, sent every run and kept 14 days), `activity` (`cdwr agent activity`, from Linear's issue history), `sessions` (each session's heartbeat with its state and detail; an `ended` one leaves the desk at once), `queue_state`, `host_metrics` (the container's load, memory and disk, kept 7 days; the desk's NUC tile), `plan_usage` (the plan's 5-hour and weekly usage from the Mac's status line, `cdwr agent statusline install`; the desk's Plan usage tile, with `usage_hours` as its hourly breakdown), and `issue_events` written by the `linear-webhook` Edge Function, `github_events` and `builds` by `github-webhook` (which also records `fly-deployment.yml` builds), `tenant_state` by the platform step below (one row per tenant plus `_shared`; the desk's Platform view), `reviews` by the daily review run, `own_actions` by every tick (what the queue did on its own, below) and `review_dismissals` by the desk's `dismiss` (env `AGENT_SUPABASE_URL` and `AGENT_SUPABASE_SERVICE_KEY`). It writes no Linear document. The desk writes only through the `desk-command` Edge Function, which checks a per-device token against `DESK_CONTROL_TOKENS` and stores each action in `desk_commands`. Its `notify` command (`{level, muteUntil}`) sets the notify dial: `run.sh` writes `notify-level` and `notify-mute-until` in the queue home (the mute file is removed for a null `muteUntil`), the files `cdwr agent notify` writes. The same desk runs on the phone as a web app the NUC serves to the tailnet (`apps/desk/Dockerfile`, the `desk` service in `apps/agent-host/compose.yaml`, `tailscale serve`; the runbook is in `tools/cdwr/README.md`, "The desk on the phone"). The scheduler applies a host's pending ones at the start of each tick, before its pause check; `limit` and `cap` land in the queue home's `limit` and `implement-cap` files, which override the PR limit of 5 and `AGENT_QUEUE_IMPLEMENT_CAP_USD`. A review row's **Copilot review** and **Merge** buttons send `copilot` and `merge`, the scheduler's GitHub writes besides its own Copilot request below: as the `codeware-agent` app, on a PR its watch holds for that ticket, after reading it again (`desk_verdict` in `watch.jq`). A merge joins main's merge queue and ends like one on GitHub; a Copilot request the app can't make falls back on `AGENT_COPILOT_TOKEN` (`tools/cdwr/README.md`).

The scheduler also requests Copilot itself. The ruleset's automatic Copilot review runs only for a PR author with a Copilot seat, so it skips every PR the app opens. When the watch reads a ticket parked on `Waiting: copilot` for an open PR that has no Copilot request or review, it asks once for that PR (`copilot_request` in `run.sh`, the same request as the desk's button, so in practice as `AGENT_COPILOT_TOKEN`) and stores the outcome as `copilotAsked` on the PR's watch entry. The 20-minute Copilot wait then counts from that request. A failed request is not retried: it sends an `action` notice, and the desk shows the wait in Waiting on you with the Copilot button, as it does for a wait no request reached within 5 minutes (the scheduler down, or the PR not yet attached in Linear).

The watch also merges an agent PR itself (COD-853), with the same enqueue as the desk's Merge button. It does so only when `merge_verdict` in `watch.jq` agrees, on its own reads. The PR passes `desk_verdict`. The ticket is `agent:review`. Its newest `**Agent: PR ready**` comment has a `Code review:` line and says `Merge: merging on its own`. No human comment is newer than that comment, and the report has no `**Ask me before merging**` line. The comment's Apply list has no `secret-*` item that isn't struck through, so a secret write always waits for Håkan's merge. The PR's complete file list matches no glob in `hold-paths.txt`. The watch reads the installed copy, beside `watch.jq`, so a PR can't change the list for itself, and the list holds itself. The ticket is not parked on a wait, since a session is then mid-round on it. The session writes that Merge line from the second line `review-diff.sh` prints, judged by the `hold-paths.txt` on `origin/main`, never the branch's own copy. The watch reads a ticket's newest 50 comments, so the check for a newer human comment holds on a long ticket too. The watch enqueues at most twice per PR and never twice on one head. When the merge queue drops a PR it enqueued once for a cause a session can fix, it sends an `info` notice and retries once on a new head: a conflict goes through the conflict pick, failing checks through the `merge queue failed` pick. Any other reason (the queue cleared, a ruleset, a rollback) and a second drop send an `action` notice and hand the merge to Håkan. A hold-paths.txt line in another form than `<glob>  # <reason>` is an error that holds every merge, never a hold dropped unseen. A PR-ready comment that says it merges on its own, but is refused for a lasting reason, sends one `action` notice per head (`held: <why>`). After the merge, the watch reads the `fly-deployment.yml` push run for the merge commit and stores `deploy` on the entry: `success`, `failure`, `skipped` (the deploy guard's `is older than` warning), `superseded` (cancelled for a newer merge's run) or `unknown` (nothing settled within 3 hours). The image workflows (`*-image.yml`) on the merge commit count too, read from the same list of push runs: a failed one makes the deploy `failure` with the run named, with its url, in `deploy.failed`, and one still running holds the deploy `pending` (`unknown` after 3 hours, named in `deploy.pending`). CI, E2E and Chromatic on main do not count. A failed or skipped deploy is never masked by a running image build. The ticket keeps `agent:review` and the audit names the run. The ticket keeps `agent:review` while the deploy is pending, and after `failure`, `skipped` or `unknown` (`queue_view.deployHold`), each of which is a `self-merge-deploy` gap in the audit.
The `queue_state` row carries an `Attended:` line saying whether an attended `/work-queue` has something to do, and `cdwr agent status` shows it too. It also carries `watch`, the host's watch.json (the PRs of agent-labelled tickets with their state, checks, Copilot review and unresolved threads), and `renovate`, its renovate.json; a Mac without the scheduler reads both for its attended rows and its wait.
Once a day, in the first idle run after 06:00, the job runs `/suggest-improvement`, which proposes one evidence-led improvement as a `Source: agent-idea` ticket or records "nothing today"; the `queue_state` row's `Suggested:` line and `cdwr agent status` show it. Accept it with `agent:ready`, discard it by cancelling with one word in a comment.
Once a day, on an idle run the suggestion leaves (after `AGENT_QUEUE_SUGGEST_HOUR` too), it runs `/review-backlog`. The run writes the queue view (the tree and the audit candidates) to `review-view.json` and the last 90 days of `review_dismissals` to `review-dismissed.json` in the queue home, each with the ticket, kind, key and fix of the stored finding it names (dismissals hold for 90 days, and the desk reads the same window), and the session writes its brief, actions and findings to `review-out/review-out.json`, a dir of its own that the container makes writable for the session user; the run reads it only as a plain file, never through a symlink. It may write only that file and `feedback_review_taste.md` in the memory directory, and it ends with `REVIEWED <n> actions` or `failed: <line>`. Then `cdwr agent review-check` validates the file and prints the row, which goes into the `reviews` table; a file it refuses, or one holding secret-like text (the table is public), stores nothing and records a warn, as does a row that could not be stored (`failed: not stored`). The session's `--disallowedTools` keep it from reading `.env*`, the cdwr files and the Linear credentials. The file's findings carry no id: the check derives each one from its kind, ticket and key, so a dismissal holds across runs. `review-ran-on` and `review-ran-at` (epoch seconds) stamp the start. The budget is `AGENT_QUEUE_REVIEW_BUDGET_USD` ($5) and `AGENT_QUEUE_REVIEW_DAYS` (1) sets the interval, 0 switching the schedule off. The desk's `review` command writes `review-requested`, which makes the next idle run a review whatever the hour or the interval (also with the interval at 0) and is removed when that run starts, before the suggestion is considered; it is refused for an hour after a review (`a review ran at HH:MM`), at once by the `desk-command` Edge Function from the newest `reviews` row, with the scheduler's own check as a backstop. The desk's `dismiss` command is handled by the `desk_dismiss` rpc into `review_dismissals` and never reaches the scheduler. The `queue_state` row's `review` column holds the last outcome, `--check` prints the gate (`review: due`, `ran today`, `requested`, `not before`, `off`) and the devlog takes an idle run only when the review does not.

Each review also lists what the queue did on its own since the review before (COD-855), the audit that stands in for Håkan's approval. The scheduler writes one event per thing at the moment it happens, to `own.jsonl` in the queue home: `merge` (a PR the watch enqueued, first seen `merged`; `left-queue` with the reason; `held` with the verdict; `refused` when it could not join the queue), `deploy` (the settled production deploy of such a merge), `apply` (each apply-list item `applied` or `refused`, its spec as the target; an invalid list is one `refused` row) and `self-deploy` (`deploy.json` settling on `ok`, `rolled-back` or `stuck` for a tag, compared each tick against the `deploy-recorded` stamp). Each event has a deterministic `event_id`. Every tick trims the file to its last 7 days and upserts it into `own_actions` with ignore-duplicates (`own_send`), so a failed send, or the time before the table's migration is applied, loses nothing. The review run then reads the rows received after the newest review that listed them (`received_at`, the database's clock, so a row sent late is listed once) and `review-check --own` puts them in the row's `own` as `{ since, until, items }`. That is code, not the session: the model can leave nothing out. A secret-like title, target or reason is withheld from its item, and a failed read stores `own` null, which never reads as "nothing". The desk shows the list above the brief, marking an item that went wrong or waits on Håkan, or the line `Nothing on its own since <date>.` After the row is stored the run sends one daily notice with the counts, up to five such items and `AGENT_DESK_URL` (`See the desk.` without it), through `notify`, so `notify-level action` never silences it.
Once a week, on an idle run the suggestion and the review leave, it runs `/devlog-draft`, which drafts at most two devlog posts in the cms from the pull requests merged since the last one, or records "nothing this week"; each draft sends an `action` notice to publish or delete it in the admin. A draft carries a meta title and a description (the `Meta title:` and `Description:` lines after its title) and the cms's `devlog` category, which `cdwr devlog draft` looks up by slug; without that category the draft fails and nothing is posted. The `queue_state` row's `devlog` column holds the last outcome, `cdwr agent status` shows the gate (due, done, not before, off), and `devlog_next` holds the same gate each tick as `{state, next, hour, text}`, which the desk shows beside the suggestions. `AGENT_QUEUE_DEVLOG_DAYS=0` turns it off.
In the container, every claude runs as `session`, whose config lives in two places: `/home/session/.claude` on the `session-claude-home` volume, and `/home/session/.claude.json` beside it in the container's own layer, which a redeploy starts empty. So the launcher trusts the checkout at every run (`session-launch.sh`, a jq merge of `projects["$AGENT_QUEUE_REPO"].hasTrustDialogAccepted`), and every run applies the project's `.claude/settings.json`, its `force-push.sh` allow rule included. The suggest, devlog and review runs only read and write their own files, so their `--disallowedTools` deny `Bash(*force-push.sh*)`; a deny wins over the project's allow.

Each tick also records the platform's state. After the desk commands and the queue lock, and in a paused tick too, `record_platform` in `run.sh` starts `cdwr agent platform-record` detached. In the container a queue run can be an hour apart, so the sleep loop also calls `run.sh --platform` on every 10-minute step between runs: the platform step alone, with no desk commands or pause check. Both run the code on `origin/main`, so a merge reaches the step within one interval. An unpaused tick fetches and moves the checkout (`to_main platform`) under its own queue lock before it collects. The `--platform` step moves it inside its detached part: it takes the queue lock without waiting, fetches, moves, installs when the lockfile changed, and drops the lock before the command starts (`platform_move`). The move is skipped while a run holds the queue lock or a live `implement.lock` (an implementing session runs in the checkout), and a paused tick doesn't move; the step then collects with the code it has. A dirty worktree or a failed fetch or install is a warn, as in `to_main`; from the detached move it only goes to `scheduler.log`. The `--platform` step is skipped when the last collection started under 5 minutes ago (`platform-ran-at` in the queue home, written by either path), so `tenant_state` is never much more than 15 minutes old. The command reads the tenants and database figures from the cms production database through `psql` (read-only SQL). The database figures also record the client connections across the whole server by `application_name`, against `max_connections` minus the reserved slots (57 on Nano), the day's peak (kept in `db-peak.json` in the queue home) and the sessions opened since the last tick (the delta of `pg_stat_database.sessions`, null on the first tick or after a counter reset). It also reads the Fly apps `cdwr-*` without `-pr-` (machines, certificates and the `GIT_SHA` that `fly-deployment-action` stamps on a deployed app), each app's health check path from its `fly.toml` (default `/api/health`, 10 s timeout) and which Infisical switches are set, as flags only, never values. Three more reads fill the `sentry`, `visitors` and `deploy` columns: Sentry error counts per `tenant` tag over 24 h and 7 d, and the open (unresolved) ones of the 24 h as `open24h` in the `sentry` json (events without a tenant tag count on the shared row; a failed read of any of the three blanks the whole column), plus the top unresolved issue and, as `fresh`, the up to 25 unresolved issues of level error or fatal first seen on production in the last 24 hours, newest first seen first (`is:unresolved firstSeen:-24h environment:production level:[error,fatal]`, the row's `tenant:<slug>` or `!has:tenant` on `_shared`, sorted by `new`) of each row with open events (a failed read of one leaves `fresh` null and `new issues: <reason>` in that row's `errors`), Umami visitors today and over the last 7 days per tenant's `statsWebsiteId`, and the newest completed `fly-deployment.yml` run on main with its deploy job (GitHub REST, signed with `PLATFORM_GITHUB_TOKEN`: `record_platform` mints an App installation token limited to actions and metadata read, passed on the command line only, so the step still holds no credential that writes; without the App it reads anonymously). Each app also gets a `behind` flag by the rule that decides a deploy: an app is behind when some machine's `GIT_SHA` doesn't hold the project's newest `<project>-<x.y.z>` release tag on `origin/main` (previews don't count). A machine on the tagged commit or a newer one is current. The step fetches the tags first (a failed fetch is noted under `behind` in `_shared`'s `errors`, and the local tags are used), and nothing is cached. Each app also carries that `latest` tag, and each machine its `version`, the newest release tag its commit holds (null when it holds none or the commit is not in the local git). It upserts one `tenant_state` row per tenant plus `_shared` (migrations `20261115130000_tenant_state.sql`: anon select, Realtime, and `20261115200000_tenant_state_signals.sql` for the new columns, both applied by hand). After the upsert it raises urgent notices for the problems `down` and a new Sentry issue: each alert goes through `<queue home>/notify.sh --level urgent --source platform <text>` with `AGENT_QUEUE_NOTIFY_STRICT=1`, so a notice that did not reach the spool or Slack exits non-zero, (no shell, and an environment of only `PATH`, `HOME` and the `AGENT_QUEUE_*`, Slack webhook variables notify.sh reads, so none of the `FLY_*`, `PLATFORM_*` credentials reach it; the text holds only names, ids, the level and the Sentry URL, never an issue title, since anon reads `notices`). A new issue is sent the first tick it is seen; a `down` app only when it is down on two consecutive ticks, so one failed health check sends nothing. Each alert goes once and again only after the problem cleared. `platform-alerts.json` in the queue home holds `{ <alert key>: { at: <first raised ISO time>, sent } }`, written after the upsert and after each notice that went out, so a loop that dies keeps the keys already told; a key whose notice exited non-zero stays `sent: false`, so the next tick tries again, and a failed prune of vanished tenants no longer stops the notices (it fails the command after them), and a key whose source failed this tick (a `fly` error on its row for `down`, a Sentry read that failed on any row or tenants not read for a new issue, a missing row when the tenants were not read) is kept, so a failed read doesn't clear it. A new issue is one key `new-issue:<shortId>` across rows, so its one notice names every row that saw it (the shared row as the host apps); older per-row `<row>:new-issue:<shortId>` keys are folded into it on read (sent if any was, the earliest time). With no file the tick seeds it and sends nothing, so the first tick after a deploy sends no burst for problems already on the desk. `--dry-run` lists the notices as steps and sends and writes nothing; without `AGENT_QUEUE_HOME` there are none. The state file is per host: only the NUC collects, since the `PLATFORM_*` credentials live in its Infisical, and a Mac that collected too would send its own notice for every problem; nothing guards against it. A tenant that has vanished is deleted only after a successful tenant read; a read that failed goes to the row's `errors`. A `platform.lock` directory keeps one run alive (stale after 5 minutes), and `AGENT_QUEUE_PLATFORM_DEADLINE` (240 s) stops a run that hangs. A failed run writes `platform-status`, which the next tick or loop step turns into a warn, at most once an hour (`platform-warned-at`). The step skips silently without `PLATFORM_DATABASE_URL`, `FLY_API_TOKEN` or telemetry. The credentials live in the agent-host Infisical `/agent-queue` folder: `FLY_API_TOKEN` (a read-only org token), `PLATFORM_DATABASE_URL` (a read-only Postgres role, which may read only the columns `platform-role.sql` grants, plus every session in `pg_stat_activity` through `pg_monitor`'s `pg_read_all_stats` (Supabase's `postgres` can grant only the former), which also shows other sessions' query text. `pg_monitor` also brings `pg_read_all_settings` (every server setting) and `pg_stat_scan_tables` (monitoring functions such as `pgstattuple` or `pgrowlocks`, where installed, which read a table under an `ACCESS SHARE` lock); it still reads no row data; run it as the database owner with `-v role=<role>` to check, adding `-v grant=1` to grant; without that membership Postgres nulls the columns of other roles' sessions, the count and the per-app sessions are recorded as unknown, and the shared row's `errors` says so) and `PLATFORM_INFISICAL_CLIENT_ID`, `_CLIENT_SECRET` and `_PROJECT_ID` (an identity with read on `/apps/*` and `/tenants/*`; the secret rotates with `cdwr agent rotate infisical platform`), and the optional `PLATFORM_SENTRY_AUTH_TOKEN`, `PLATFORM_SENTRY_ORG`, `PLATFORM_UMAMI_URL` and `PLATFORM_UMAMI_API_KEY`; without one of these the read is skipped and `not configured` shows in the row's `errors`. `run.sh` unexports them and passes them only on that command's line, so no claude run inherits them. The agent image carries PGDG's `postgresql-client` and a pinned `flyctl` for it. `jq` comes from its release, pinned to 1.7+, because bookworm's 1.6 exits 0 on empty input under `-e`.
The desk raises these problems from the rows (the rules live in `libs/shared/util/platform-problems`, which `cdwr agent platform-record` reads too, for its urgent notices below):

- app down: health not 200 or timed out (10 s), or the app has no machine at all (a suspended or stopped machine is not down)
- behind main: the `behind` flag, an app whose machines don't all hold the newest release tag
- certificate not ready: neither Ready nor unknown
- Postgres connections near the limit: 80% or more (46 of 57) of the usable connections, counted across the whole server; the evidence names the top three applications and the day's peak. A row without a limit raises none. Pooler sessions are information only
- error spike: 10 or more open (unresolved) errors in 24 h and at least 3x the daily average of the 6 days before; the row shows the total and the open count
- new Sentry issue: an unresolved issue of level error or fatal first seen on production in the last 24 hours (the `fresh` list of the `sentry` json), one problem per issue, warn on the desk; it leaves the list after a day, so it is raised once, and the notice names its short id, level and the Sentry URL, not the title. The evidence names its short id, level, title and first-seen time, and the sheet links the issue in Sentry
- deploy failed: the newest run's deploy job failed; clears when a newer run's deploy doesn't fail
- backup stale: the newest database dump is more than 26 hours old, or there is none yet while the backup is set up; a failed last run is its evidence

Each night the tick also backs up the cms database. Right after the platform step, and also while paused, `record_backup` in `run.sh` starts `cdwr agent backup` detached, at the first tick from 02:00 local time on a day `backup-ran-on` doesn't name yet. The date is written when it starts, so a failing night is not retried every tick. The command dumps the `payload` schema with `pg_dump` (plain `schema.sql` and `data.sql`, as `cdwr db backup` writes them) into `backups/cms-production-<stamp>/` in the queue home (owner-only). The url reaches `pg_dump` through libpq's `PG*` variables, never its arguments. The dump is written to a hidden `.partial` folder and renamed once complete. After a good dump only the newest 7 are kept; a failed one prunes nothing. Each run writes `backup-status.json` (`at`, `ok`, `name`, `bytes`, `error`, with urls stripped). The platform step reads the folder and that file into the `backup` column of `_shared` (`newest`, `newestAt`, `count`, `bytes`, `lastRun`; migration `20261116120000_tenant_state_backup.sql`, applied by hand), which the desk shows in the shared row's sheet. A `backup.lock` directory keeps one run alive (stale after 20 minutes), `AGENT_QUEUE_BACKUP_DEADLINE` (900 s) stops a hung one, and a failure writes `backup-failed`, which the next tick turns into a warn at most once an hour (`backup-warned-at`). The step needs only `PLATFORM_BACKUP_DATABASE_URL`, in agent-host Infisical `/agent-queue`: the session-pooler url of a `backup_reader` login role with usage on `payload`, select on its tables and sequences, and default privileges for the tables later migrations add. A dump holds password hashes and tenant api keys, so it is as sensitive as the database. The agent image installs PGDG's `postgresql-client` of a pinned major (`PG_CLIENT_MAJOR`), since `pg_dump` refuses a newer server. The volume's nightly tarball (`apps/agent-host/nuc/backup-agent-home.sh`) leaves `backups/` out. To restore, copy a dump folder into `backups/` of a checkout and run `cdwr db restore` there.

The desk's `restart` and `gate` commands use a separate, writing set in the same folder: `DESK_FLY_TOKEN` (an org deploy token, with an expiry; it and the platform step's `FLY_API_TOKEN` rotate with `cdwr agent rotate fly`), `DESK_INFISICAL_CLIENT_ID`, `_CLIENT_SECRET` and `_PROJECT_ID` (production write on the project; the secret rotates with `cdwr agent rotate infisical desk`), and `DESK_SUPABASE_DB_URL` (the apply list's migrations, below). They are unexported the same way and named only on the command line of the `cdwr` call that applies a command, never on the platform step's. The command is dry-run first, the verdict is checked, then the row is acked and the real command runs. A `close` always generates the site password, which stays in Infisical (`/tenants/<tenant>/apps/<app>`, `SITE_GATE_PASSWORD`) and never reaches a row, log or notice. The three database urls, `PLATFORM_DATABASE_URL`, `PLATFORM_BACKUP_DATABASE_URL` and `DESK_SUPABASE_DB_URL`, get a new role password with `cdwr agent rotate db-role <platform|backup|desk>`, run on the Mac. `AGENT_SUPABASE_SERVICE_KEY` is the NUC's own Supabase secret key, apart from the Mac's `default` key and the edge functions' injected one, and `cdwr agent rotate supabase`, run on the Mac, replaces it and deletes only the NUC's old key; the legacy JWT keys stay enabled. Details are in `tools/cdwr/README.md`.

## Apply list

A PR that needs production steps after it merges lists them in its `**Agent: PR ready**` comment, under the hand-off checklist, as an `Apply list:` block. The scheduler applies them after the merge, so Håkan doesn't. The block is checkbox lines:

```
Apply list:
- [ ] restart cdwr-cms
- [ ] scale cdwr-cms 2 after-deploy
- [ ] supabase-migration tools/cdwr/agent-queue/supabase/migrations/20261120120000_x.sql
- [ ] deploy-workflow cms production
- [ ] agent-deploy
```

The header is `Apply list:`, bold or plain. Blank lines are skipped and any other line ends the block. The scheduler edits the comment in place and writes the outcome after `·`: a ticked box is `applied <time>` or a note such as `already 2`; an unticked item with `refused: <why>` was not applied; `~~item~~` is dropped by hand. An item with no outcome is pending. An item that is neither ticked nor dropped is open, and counts as waiting on the desk: a merged ticket stays there until its list is applied, refused items too.

Each line is a kind and its arguments. The patterns are closed, and they are the security boundary. Any other kind, a wrong argument count or an argument that fails its pattern makes the whole list invalid, and nothing from it is applied.

| Kind                 | Arguments                                   | Rule and credential                                                                                                                                                                                                                                    |
| -------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `restart`            | `<app>`                                     | `cdwr-cms` or `cdwr-(cms\|headless)-<slug>`. `DESK_FLY_TOKEN`.                                                                                                                                                                                         |
| `scale`              | `<app> <count>`                             | App as above, count 1 to 4. `DESK_FLY_TOKEN`.                                                                                                                                                                                                          |
| `deploy-workflow`    | `<project> production`                      | A project in `release.groups.apps.projects` of `nx.json`, environment literally `production`. The GitHub App token, which needs Actions write.                                                                                                         |
| `supabase-migration` | `<file>`                                    | `tools/cdwr/agent-queue/supabase/migrations/<14 digits>_<name>.sql`, and the PR must add it. `DESK_SUPABASE_DB_URL`: a role that may run DDL in `public` only. The `public.applied_migrations` ledger records what ran.                                |
| `supabase-function`  | `<name>`                                    | An existing folder under `supabase/functions/`. Refused as `not enabled` for now.                                                                                                                                                                      |
| `agent-deploy`       | none                                        | No credential. Waits for the self-deploy's `deploy.json` to reach phase `ok` on the merge sha or newer. Refused as `no self-deploy on this host` when there is no `deploy.json`.                                                                       |
| `secret-copy`        | `<env> <folder> <from> <to>`                | Copies one Infisical secret to a new key in the same folder, never over an existing value (the same value ticks as `already copied`). `cdwr infisical copy-secret`. `DESK_INFISICAL_*`.                                                                |
| `secret-rewrite`     | `<env> <folder> <key> host=… port=… user=…` | Changes only the host, port or user of a url secret; the password and the rest stay byte for byte, and a rewrite that would change the password is refused. `cdwr infisical rewrite-url`. `DESK_INFISICAL_*`.                                          |
| `secret-set`         | `<env> <folder> <key> <value>`              | Sets a non-secret config value the PR states: a whole number, `true`/`false`, or an `https://` url without credentials. The list is a snapshot taken when the merge is first seen: the watch stores it as `apply` in `watch.json`, with the merge commit. Only the agent's own PR-ready comment counts, and later edits to it add nothing. A trailing `after-deploy` makes an item wait for the `fly-deployment.yml` run on the merge commit. A failed run refuses it as `production deploy failed`; 3 hours without a run refuses it too.

The scheduler applies the items in order. Each one goes through `desk_cdwr` as a dry run first, then the real call, as the desk's commands do. It stops at the first failure and sends one `action` notice. An item whose credential is missing is refused as `no <VAR> on <host>`, and a migration whose file on main no longer reads as it was merged is refused too. Each outcome is saved to `watch.json` before the next item runs, and nothing more runs when that save fails. A tick Linear did not take is tried again on the next run, never the item. A refused item stops the list for good: the list is read once, at the merge, so a later edit of the comment (a deleted outcome, an item struck through) changes nothing the scheduler does, and what is left is Håkan's. While a list is open, the merge notice names it in place of the plain hand-off notice.

The three `secret-*` kinds (COD-852) write to Infisical with the NUC's desk identity, which has production write. Whether it may also read and write `preview` is part of the hand-off check of its role; until that is confirmed a `preview` item fails at the dry run and stops the list, so a session posts `preview` items only once this README says the role covers it. `preview` stays in the vocabulary because the Done-when replay runs it as Håkan. The vocabulary is the narrowing: `<env>` is `production` or `preview` (never `development`), `<folder>` is `/apps/<app>` or `/tenants/<slug>/apps/<app>` (never `/agent-queue`, where the desk's own credentials live), keys match `[A-Z][A-Z0-9_]*`, and `DEPLOY_ENABLED` and `SITE_GATE_PASSWORD` belong to other commands. `run.sh` re-checks every pattern before the call, whatever the session checked. No value ever leaves the command: the dry-run json carries the environment, folder, key and the state (`absent`, `same`, `different`) with a url's host and port, the outcome names keys, folders and shape (`host a → b, port 5432 → 6543`), and errors are scrubbed of every value the command read or wrote. If Infisical's plan offers path conditions on a role, Håkan narrows the identity to `/apps/**` and `/tenants/**` in production and preview; until then the vocabulary is the only narrowing. A new credential (a password nobody holds yet) is never derived: creating it stays Håkan's.

Before posting the comment, the session runs `cdwr agent apply-list check --body <file>`, which validates the block by the same rules and says which line is wrong.

When that work waits and no session is alive, the job starts one itself: `implement.sh` runs
`claude -p "/work-queue implement-only once key=\"<key>\""` detached, with deny-by-default permissions, a
per-run budget (`AGENT_QUEUE_IMPLEMENT_BUDGET_USD`, $15) and a daily cap
(`AGENT_QUEUE_IMPLEMENT_CAP_USD`, $40) kept in `implement-spend.jsonl`. It resumes approved,
answered or reviewed work only (a `plan approved` pick, an answered gate, a review, and `merge checks`
below), and never starts a new ticket. It reaches Linear on both hosts
through Linear's own MCP server, signed with a token of the queue's own Linear app, so its writes
are the app user's and not Håkan's (`AGENT_QUEUE_LINEAR_MCP`, the credentials and the token cache
are in `tools/cdwr/README.md`); a run without Linear tools doesn't start. In the container the
runs reach it through a local proxy (`apps/agent-host/linear-mcp-proxy.mjs`) that signs the requests
and answers a call to a tool outside `linear-tools.txt` itself, the one Linear tool list; the session
gets no token. Every claude run, planning, suggestion, review, devlog and implement, runs as a
second user there, `session`, launched through sudo by `claude_launch` in `lib.sh`: it reads the
queue's checkout and the queue home and writes only the sessions dir, the notice spool,
`devlog-drafts/` and `review-out/`, its memory is the session's own, its ticket worktrees hang off a clone of its own (`/work/codeware-session`,
`AGENT_QUEUE_WORKTREE_REPO`), and the tmpfs keys, the checkout's `.env` and `/proc` of the queue's
processes are out of its reach; the devlog reaches the cms through `devlog.sh`, which crosses back
to `agent`; the two users and their sudo crossings are described in
`apps/agent-host/README.md`. It also answers `POST /attended` with the attended query's JSON, run as `agent`
through `lib.sh attended`, so a session without Linear credentials can still compute its pick:
`wait.sh` falls back to that route when `linear_auth` fails and the proxy port is set, and only
the attended query goes that way. In the same spirit a session's notices go into the spool that
`AGENT_QUEUE_NOTIFY_SPOOL` names (see **Notices** below). A queue file, `linear-tools.txt` is installed
beside the scripts. The queue tells its own
comments from Håkan's by that author (`is_agent` in `watch.jq`), and never starts a ticket whose
`agent:ready` the app added (`refused` in the queue view). On GitHub it acts as the
`codeware-agent` app (`github-app.sh`, credentials in `tools/cdwr/.env`), never as Håkan, so
main's rulesets apply to it; without the app it does not start. The session takes the key's work
first (`wait.sh --runnable` lists what it may take); when it can't, it ends with
`not tried: <key> · <reason>` and the launch is recorded `untried` and not counted. Before its PR the
session runs the code review over a diff file: `review-diff.sh <worktree>` writes the branch against
`origin/main` plus the uncommitted changes into the worktree's git dir and prints the path, since the
run may neither pipe git into a file nor diff against `origin/main` itself. A session whose review
could not run at all ends with `review failed: <key> · <reason>` and opens no PR; the launch is
recorded `failed` with that reason, one notice goes out, and the ticket keeps `agent:working` with its
**Next:** line naming why, so the desk shows the gap. A session cut short by a deploy or
container stop is recorded `interrupted` and not counted either. After two
launches that change nothing it stops and sends the "Start /work-queue" notice instead. `cdwr agent pause` stops
launching too.

Implement sessions start in the container only. Elsewhere (a Mac with the launchd job) `run.sh`
turns a launch into a notice with the reason `implement runs only in the container`, so the Mac
plans and notifies and never counts a miss; `implement.sh` refuses to start outside the
container as a backstop, before its lock, with a `failed` row and no notice. In the container,
`secrets.sh` writes the key secrets (`AGENT_GITHUB_APP_KEY` to `app.pem`, `AGENT_QUEUE_LINEAR_KEY`
to `linear.key`, the Linear app's client id and secret to `linear-app.env`) to the `/run/agent`
tmpfs, mode 600, and never exports them, so no process's `/proc/<pid>/environ` holds them; in
plain `.env` mode Docker still puts them in tini's `/proc/1/environ`. The session's deny rules
cover `/run/agent`, `/proc` (Read, which Grep and Glob follow, and any Bash command naming it) and
every `tools/cdwr/.env` (it holds the Supabase service key), and an implement session's ticket
worktrees get no copy of that file (`envCopiesFor` in `agent.logic.ts`). `CLAUDE_CODE_OAUTH_TOKEN`
and `AGENT_SUPABASE_SERVICE_KEY` stay in the loop's environment, and tini's environ keeps the
Infisical identity, until the session runs as a uid of its own (COD-653).

Checks are never hand-offs. Before the merge, the session runs what it can on the preview and lists
it in the PR-ready comment under `Checked on the preview:`. After the merge, checks go under
`After the merge, the agent checks:` as `- [ ] <check>` items, apart from the hand-off checklist.
Once the PR merged 15 or more minutes ago and every hand-off is ticked or dropped (a deploy comes
first), `watch.jq` (`merge_checks`, `merge_checks_due`) makes a `merge checks` pick. An implement-only
run takes it, ticks each passing check, strikes a failing one (`- [ ] ~~check~~ failed: <what>`) and
posts `**Agent: checks**` with what it saw. A failure also gets an `**Agent: suggestion**` for a
follow-up ticket. Only a check that needs Håkan's logged-in browser stays a hand-off, and says why.
For these the session may run `pnpm cdwr agent status` and `logs` (not with `--host`) and fetch
`cdwr.io`, `*.cdwr.io`, `codeware.se` and `*.codeware.se` only. `*.fly.dev` is not listed: a wildcard
there would let a session send data to any Fly app.

A claude run that ends on the plan's session limit (`You've hit your session limit · resets 7:10am (UTC)`) is recorded `limited`, with the limit text in its detail. It is not a failure. The run writes `limited-until.json` in the queue home, `{"until": <epoch seconds>, "text": "<limit text>", "at": "<ISO>"}`, and while `until` is in the future no claude run starts: planning, implementing, suggest, review and devlog all wait. The reset is the next occurrence of `resets H[:MM]am|pm (<zone>)` in the text; a text without a parseable reset holds for 60 minutes, and no hold lasts longer than a day. Suggest, review and devlog give their day stamp back when they end limited, so they run again after the reset. A limited implement launch is given back every time, so it never counts toward the two-launch stop above. The implement launch decision reads `notify` with the reason `session limit, resets 07:10 UTC`, `--check` prints `limit: claude runs held until 07:10 UTC` before its other lines, and `cdwr agent status` shows `held by the session limit until 07:10 UTC` on its implement line while the file is in force. The desk shows it amber, a third state between ok and problem: the Agent health page reads `session limit` and the run row takes the warning style, until a later run goes well.

An attended Mac session stays visible to the NUC because its session hook copies each session file into the NUC's container (`cdwr agent mirror set --host agent-host`, once). So the NUC launches nothing a live Mac session holds: while that session is polling, any other ticket may launch there; while it is working, only a comment on a merged ticket does. The claim line decides who has a ticket, and a session that loses the race leaves it alone. The hook runs from the checkout the session started in, which must be on a main that includes the mirror support: `cdwr agent attend` does that.

Every run also audits the tickets (`audit` in `watch.jq`), report-only: it changes nothing in Linear. A gap is a state the queue cannot resolve by itself, and each carries what is wrong and the one fix. The kinds are `held`, `ready-planned` (a plan nothing will take: an `agent:ready` ticket with a Status table that is neither a `plan approved` pick nor waiting on a gate), `review-no-pr`, `merged-not-done`, `closed-pr`, `label-on-closed`, `two-labels`, `needs-input-no-question`, `unlabelled` and `launch-guard`. Four more are candidates for a later AI review, worded "check" and marked `candidate: true`: they stay in the view's audit and the tree's `gaps`, but send no notice and are not in the `Gaps (n)` count: `done-with-open-rows` (a ticket Done within 14 days whose Status table still has rows other than Done, Dropped or Skipped), `parent-status-stale` (a Status row naming a sub-issue says the opposite of its state), `untouched` (open, no agent label, not updated for 10 days, its parent updated since) and `decision-unasked` (a Status row says decision or Håkan picks, with no `agent:needs-input` and no agent question). The Status column is the one headed State or Status, else the last. A gap's `what` stays short and its `rows` array carries the row texts. They read every open COD ticket plus those Done within 14 days (`TREE_QUERY` in `lib.sh`, read by the run only, `AGENT_QUEUE_TREE_PAGES` pages of 50 at most, 10 (500 tickets) by default, with a warn in `scheduler.log` on a fresh read that leaves tickets out, kept in `tree-nodes.json` for `AGENT_QUEUE_TREE_TTL_MIN` minutes, 15 by default, and reused when a read fails), where the other kinds read the agent tickets. The audit and a `tree` of every open COD ticket, as roots with their sub-issues, are keys of the queue view, so `queue-view.json`, `queue_state.view`, `cdwr agent status` (a `Gaps (n)` note) and the desk (a Gaps group on the queue sheet, and the Ticket tree page, the Tree page of the Agent view, with each ticket's state, agent label, pick position (`position`: its 1-based place in the order `next` and the held tickets give, null when the queue never picks it; roots and children sort by the lowest position in their subtree, then by `queue_order`), PR, open blockers and gaps, its plan progress, live session, PR checks and age, and Open/All and Gaps-only filters) show them. The desk's header search finds a ticket by id or title among everything the desk has loaded, and opens a Ticket sheet (`#ticket/COD-n`) with all the desk holds for it. A stale claim or an unclaimed working ticket is no gap: the pick already takes it over. `audit-seen.json` maps each gap id to `{ first, told }`: a gap that has stood for 15 minutes and was not yet told sends one action notice, `Gap: <what>. <fix>`, so a state that settles by itself stays quiet; more than 3 due in a run send one summary instead; a gap that closes and returns starts over. `--check` sends nothing. The audit output goes through files, never arguments, since it outgrows the argument limit.

## Notices

Every notice leaves through `notify.sh`, with one of three levels: `urgent` (Håkan must attend: a run or implementing session that failed or hit its cap, no Linear tools, a failed backup or platform step, a tenant going down or a new production Sentry issue (source `platform`, from `cdwr agent platform-record`), a self-deploy rollback or stuck, a credential readable where claude runs), `action` (something waits on him: gates, gaps, ideas, devlog drafts, "no session running", a held merge, the daily own-actions notice) and `info` (progress). A call without `--level` is `action`. `run.sh` calls it as `notice <level> <source> <message>`, `implement.sh` as `notify <level> <message>`, and neither falls back to `~/.claude/hooks/notify-slack.sh` any more.

- **Spool.** `notify.sh` writes `{text, level, source, ticket, at}` as `<epoch>-<pid>.json` into the spool when `AGENT_QUEUE_NOTIFY_SPOOL` names one (the container's sessions, which hold no webhook), or into the queue home's `notify-spool` when `notices-drained-at` says a drain reached Supabase under 30 minutes ago. It never holds the key, so that stamp is how it learns a drain is alive.
- **Drain.** `notices_drain` in `telemetry.sh` upserts each spool file into the `notices` table (id `<host>:<file name>`, so a resend is ignored) and removes it. `run.sh` drains on every tick, a paused or platform one too; the container's sampler drains as well. A pass with no failed insert stamps `notices-drained-at`.
- **Deploys.** The `github-webhook` function is a third writer, host `github` and source `github-webhook`: a completed `fly-deployment.yml` run becomes one row, id `github:fly-deployment:<run id>:<run_attempt>`, written with `ignore-duplicates` so a redelivery never resets a forwarded row. A failed production deploy is `urgent`, any other failure `action`, a success whose `build` job ran `info`; cancelled runs give none. It replaces the workflow's own Slack job.
- **Forwarder.** Only the container forwards: `relay_notices` in `apps/agent-host/entrypoint.sh` reads up to 50 `pending` rows, oldest first, every host's, posts those the dial lets through and marks them `forwarded`, and marks the rest `held`, so turning the dial up later replays nothing. A failed post stays `pending`. An urgent post starts with `:rotating_light:`.
- **Dial.** `notify-level` in the forwarding host's queue home is `urgent`, `action` or `all`; missing or unknown reads as `urgent`. Until the ISO time in `notify-mute-until` only urgent passes. `notify.sh --passes <level>` is the one copy of the rule, and `notify.sh --dial` prints it as `{level, muteUntil}`, which `queue_state.notify` carries. `cdwr agent notify [urgent|action|all] [--mute-until <time|off>]` sets both.
- **Fallbacks.** A host without the key posts straight to Slack, filtered by its own dial: `notify.sh` when no drain stamped, and the drain for anything already spooled. An urgent notice still in a spool 10 minutes after its `at`, its insert failing, is posted straight to Slack by the host that holds it.

## Self-deploy

The NUC deploys the agent image itself, so a merged change to the queue reaches the container without `cdwr agent deploy` as a hand-off. The host timer `cdwr-agent-deploy.timer` runs `apps/agent-host/nuc/self-deploy.sh` as `cdwr` every 5 minutes. The container has no Docker socket. The script reaches in only through `/opt/agent-queue/deploy-gate.sh`, run by `docker exec`, and each subcommand reads or writes files in the queue home:

- `state` prints `none`, `waiting` or `working`, by the lock rules `cdwr agent deploy` reads over ssh
- `pause` touches the paused file and prints `created` or `kept`; `unpause` removes it
- `job` prints `job.json`, the last run's report
- `record` writes `deploy.json` from the JSON object on stdin, keeping only the known fields
- `nuc-record` writes `nuc-apply.json` the same way, for the host installer below
- `notify <text>` sends an urgent notice from the source `self-deploy`; the script runs it through `/opt/agent-host/secrets.sh`

A tick and `cdwr agent deploy` never run side by side. Both take `flock` on `/opt/cdwr-agent/deploy.lock`. A tick holds it from start to exit, and skips itself when the lock is taken. `cdwr agent deploy` holds it through one open ssh (`flock … cat`) from before the pause to after the record, and waits for it as long as `--wait`. The kernel drops the lock when its holder exits or the ssh connection drops, so no stale lock is left behind.

Each tick does one of two things. While the last deploy waits for its first run (phase `checking`), it checks that run. Otherwise it looks for a newer build.

- The build is the newest green `agent-host-image.yml` run on main, read from GitHub's REST API, signed with the host's read-only token when it is installed (`apps/agent-host/README.md`, "GitHub reads and the read-only token"). The tag is `sha-` and the first 7 characters of that commit. The compose file comes from raw.githubusercontent at the same sha, so the image and its compose file always match.
- It skips a tag that is already running, one that was rolled back (until main builds a newer one), and one held by `cdwr agent deploy --tag`.
- It deploys nothing while the queue is paused by hand.
- It pauses the queue and waits up to 30 minutes for it to be quiet (`none` or `waiting`). If the queue stays busy it resumes and tries again on the next tick. It checks once more after the pull, since the pull takes minutes.
- It writes `image.env` and `compose.yaml`, keeping the old ones as `image.env.previous` and `compose.yaml.previous`, pulls, runs `up -d agent`, and resumes the queue it paused.

The health check judges the first run of the new container:

- ok: a `job.json` newer than the deploy, from the new image sha, with nothing in `differs`. It is also ok when `differs` lists files but main has a newer `agent-host-image.yml` run, whether it is running, failed or green (a green one gets deployed), or when `differs` is null because that run could not read main.
- wait: `differs` lists files and the newest run on main is the deployed one. A paused tick compares with the main it fetched last, so a later run may still clear it.
- rollback: the container is not running (after 2 minutes), or there is no healthy run in 20 minutes (a `differs` that stands until then included). The script puts the `.previous` files back, runs `up -d agent`, remembers the tag as failed and sends an action notice (through `secrets.sh`, which holds the Slack webhook). Without `.previous` files it goes `stuck`, which the desk shows as a problem, and sends the same notice.
- superseded: `image.env` names another tag, so a deploy by hand took over and there is nothing to check.

The state is in `self-deploy.json` in `/opt/cdwr-agent` (`phase`, `tag`, `previous`, `at`, `failed`). `cdwr agent deploy --tag` for a tag older than the newest build writes `hold` there, so the timer leaves that tag alone. A deploy without `--tag`, or a newer green build on main, clears the hold.

- A read of the builds that fails is logged and tried again next tick. The hourly limit used up at once, any other failure after 30 minutes, makes `deploy.json` read `stuck` with the reason (`rate limited until HH:MMZ`, say) and sends one urgent notice; the first good read puts back the record it replaced (`readFailingSince`, `readNoticed` in `self-deploy.json`). Meanwhile a deploy being checked is not rolled back at its deadline. A token GitHub refuses is told once and not sent again until its file is replaced (`apps/agent-host/README.md`, "GitHub reads and the read-only token").

The script writes each step to the container through `record`, which makes `deploy.json`. The scheduler's telemetry carries it as `queue_state.deploy`, and the desk shows it on the Agent health page (the tag, the one before, the phase and any reason).

The first deploy is by hand, from the Mac: `cdwr agent deploy --host agent-host`. The script does nothing until `image.env` and `compose.yaml` exist, and it needs an image that already has `deploy-gate.sh`. The host needs `curl`, `jq` and `flock`. Installing the timer is in `tools/cdwr/README.md`, "The NUC". Its log is `journalctl -u cdwr-agent-deploy`.

### Host installer

What runs on the host itself, the scripts and systemd units in `apps/agent-host/nuc`, reaches it the same way, pulled by the host. `cdwr-agent-nuc.timer` runs `nuc-sync.sh` as `cdwr` every 5 minutes. It reads main's head, then the newest commit in that head's history that touches `apps/agent-host/nuc`. When that commit is not the one it last applied or failed, it runs `sudo -n /usr/local/sbin/nuc-apply <sha>`, the only thing `cdwr` may run as root. It writes the outcome (`sha`, `main`, `at`, `phase`, `changed`, `reason`) to `/opt/cdwr-agent/nuc-apply.json` and, through `deploy-gate.sh nuc-record`, to `nuc-apply.json` in the queue home, where the apply kind `nuc-install` reads it. A record the container did not take (a self-deploy may be restarting it) is sent again on later ticks. A failure sends one action notice and is not retried until main changes the folder again, or `/opt/cdwr-agent/nuc-apply.json` is removed. A failed GitHub read, a rate-limited `nuc-apply` (exit 75) included, is no failure: it is tried again next tick, leaves `nuc-apply.json` alone, and sends one notice once it has lasted 30 minutes. What `nuc-apply` installs, and what it will not do, is in `apps/agent-host/README.md`, "The root installer". Its log is `journalctl -u cdwr-agent-nuc`.
